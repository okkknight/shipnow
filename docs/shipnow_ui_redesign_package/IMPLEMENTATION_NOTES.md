# ShipNow UI 重构实现要点

这份文档把 `shipnow_ui_redesign_package` 里的设计要求拆成可执行实现项，并标注哪些只是样式改造，哪些会影响业务逻辑。

## 目标

- 把 ShipNow 从 dashboard-first 改成 chat-first 工作台
- 保留现有的项目创建、Codex 修改、预览发布、失败回看能力
- 让主界面只呈现用户下一步最需要的动作
- 把工程信息、任务日志、路径、发布记录收纳到辅助区域
- 视觉、组件、字体、颜色、切图、布局细节都以 UI 图为最终标准

## 当前实现和目标的差异

现有实现已经具备：

- 项目创建、apply change、rebuild、publish、delete
- SQLite 记录项目、任务、发布记录
- preview / public 静态发布链路
- 任务日志轮询

但当前 UI 仍然偏向 dashboard：

- 顶部统计卡片
- 项目表格
- 右侧 tabs 详情页
- 创建项目弹窗是表单式入口

设计包要求把这些内容改成：

- 左侧项目抽屉
- 中央对话式工作区
- 右侧状态抽屉
- 底部常驻 composer

## 实现要点

### 1. 先改应用骨架

要先重构页面结构，再处理细节样式。

建议目标结构：

- 左侧：项目与模板抽屉
- 中间：当前项目对话工作区
- 右侧：状态、链接、任务、发布记录抽屉

这一步会影响：

- `src/App.tsx`
- 响应式布局逻辑
- 移动端抽屉交互

真实路由建议按下面的键分工：

- 工作台和内部页面使用 `projectId`
- 公开预览和线上站点使用 `publicHandle`
- `displayName` 只负责 UI 展示和同步编辑入口

### 2. 首页从 dashboard 改成创建入口

`/shipnow` 应该首先是“创建项目”的入口，而不是统计面板。

首页应保留的元素：

- 一句话输入
- 模板 chips
- 最近项目
- 新建入口

首页应移除或收纳的元素：

- Projects / Active / Published / Failed 统计卡片
- 项目表格

### 3. 当前项目页改成 chat workspace

当前项目页应该以对话为中心：

- 用户需求消息
- ShipNow 回复消息
- 执行中状态
- 结果卡片
- 快捷 chips
- 底部输入框
- 预览 / 发布常驻按钮

现在的 `overview / tasks / releases / logs` tabs 应该收敛到右侧状态抽屉或高级区域。

### 4. 状态展示要翻译成用户语言

页面主流程中不要直接暴露工程状态名。

建议映射：

- `generating` -> 正在处理 / 正在修改
- `preview_ready` -> 预览已就绪
- `build_failed` -> 修改失败
- `publishing` -> 正在发布
- `published` -> 已上线
- `publish_failed` -> 发布失败

### 5. 预览和发布必须常驻

设计包要求预览和发布入口始终可见。

这意味着：

- 不能把发布藏到二级 tabs 里
- 不能让预览只出现在项目列表里
- 移动端也要有明确主按钮

### 6. 失败态必须带下一步

失败态不是纯报错。

至少要提供：

- 自动修复
- 恢复上一版
- 查看技术日志
- 重新发布

### 7. 移动端必须单列 chat-first

手机端不能保留 dashboard 的多列和密集表格。

必须重点处理：

- 单列布局
- 底部固定输入区
- 抽屉覆盖式打开
- 按钮触控尺寸
- 键盘顶起时的滚动和留白

### 8. 首页和项目页要有模板辅助

模板不是复杂配置页，只是降低创建门槛的辅助入口。

建议模板 chips：

- 产品官网
- 个人主页
- 小游戏
- 工具站
- 活动页
- 空白项目

## 业务逻辑可能需要改的地方

### 1. 项目入口最好路由化

现在项目选择主要靠本地 state。

如果要符合设计包的页面结构，建议引入可恢复的路由状态，例如：

- `/shipnow`
- `/shipnow/project/:projectName`
- `/shipnow/preview/:projectName`

这不是纯 UI 改造，会影响路由、页面初始化、刷新恢复、外链进入行为。

### 2. 项目命名要拆成三层字段

最终约定如下：

- `projectId`：内部固定 ID，永不变
- `displayName`：UI 展示名，使用同一套 ASCII 规范
- `publicHandle`：公开 URL 片段，使用同一套 ASCII 规范

规则要求：

- `displayName` 和 `publicHandle` 默认取同一个值
- 两者都不能包含中文、空格和特殊符号
- 只允许小写字母、数字和短横线
- 用户修改 UI 名字时，`displayName` 和 `publicHandle` 同步更新
- 旧 `publicHandle` 进入别名表，并永久保留重定向解析能力

这样做的原因：

- 避免一个字段同时承担展示名、URL、内部标识三种职责
- 保持 UI 名称与公开地址一致
- 内部关联始终靠 `projectId`，避免重命名破坏任务、发布和日志引用

### 3. 创建项目流程可能要调整

现在创建需要 `name + title + prompt`。

设计包更偏向：

- 用户先用一句话开始
- 项目名可以系统生成，或后置编辑
- 模板 chips 只是辅助，不是复杂表单

如果要按设计落地，创建业务流要简化。

### 4. 建议补一层消息或事件记录

当前后端存的是：

- 项目
- 任务
- 发布记录

但设计包要的是可回放的对话式体验。

如果要让“用户消息 / ShipNow 回复 / 结果卡片”长期可见，必须增加消息或事件记录层，并记录：

- 完整对话消息
- 任务事件
- 状态变更
- 结果卡片
- 发布前后的关键步骤

如果不加，只靠任务和发布记录反推，体验会偏弱。

### 5. 发布前确认最好变成独立步骤

设计包要求发布前确认目标地址。

这意味着发布流程不只是一个按钮点击，而是：

- 先确认
- 再发布
- 再显示成功 / 失败反馈

后端接口可以不变，但前端流程会变化。

### 6. 路由键和公开访问键的边界

建议固定为：

- `projectId`：内部唯一且稳定的关联键
- `publicHandle`：公开访问键，用于站点路由
- `displayName`：界面显示名，与 `publicHandle` 同步编辑

实现时不要把 `projectId` 暴露给用户访问路径，也不要让 `publicHandle` 参与内部主键和文件系统主目录。

### 7. 自动修复最好有独立动作

设计包里的“自动修复”不是简单文案。

如果要真的支持它，需要：

- 新任务类型
- 或者基于失败摘要的修复入口

这属于业务逻辑扩展，不是样式改动。

### 8. 状态映射最好独立成层

不要让页面直接到处判断内部状态名。

建议单独抽：

- 内部状态 -> 用户状态
- 用户状态 -> 可用动作
- 用户状态 -> 视觉样式

这样后续扩展更稳。

## 可以直接复用的现有能力

以下能力不需要推倒重来：

- 项目创建 / 修改 / 重建 / 发布 / 删除的任务框架
- preview / public release 的文件落盘模型
- SQLite 记录的项目 / 任务 / 发布历史
- 任务日志轮询
- reserved project name 校验
- 删除二次确认

## 推荐实现顺序

1. 先做 AppShell 和布局重构
2. 再做首页创建入口
3. 再做当前项目 chat workspace
4. 再做右侧状态抽屉
5. 再做发布确认与失败修复
6. 最后补移动端细节和视觉统一

## 不建议在这一轮做的事

- 多人协作
- 复杂版本回滚
- 模板市场
- 权限系统
- 复杂统计 dashboard
- 任务队列可视化
