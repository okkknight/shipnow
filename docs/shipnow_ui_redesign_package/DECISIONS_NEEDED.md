# ShipNow UI 重构需要拍板的决策

这份文档列出会影响实现方向、并且需要你先确认的点。没有这些决策，后续只能先做保守方案。

## 已确认方向

下面这些点已经由你确认，后续实现按这个方向走：

- 视觉、组件、颜色、字体、切图和布局都以 UI 图为最终标准
- 路由全部走真实路由
- 工作台和内部页面使用 `projectId`
- 公开站点和预览使用 `publicHandle`
- `projectId` 作为内部固定关联 ID
- `displayName` 和 `publicHandle` 都使用同一套 ASCII 规则
- `displayName` 和 `publicHandle` 默认同值
- 用户修改 UI 名字时，`displayName` 和 `publicHandle` 同步更新
- 旧 `publicHandle` 进入别名表，并永久保留重定向解析能力
- 首页模板 chips 只是预填 prompt
- 右侧状态区展示粒度以 UI 图片为准，只保留普通用户关注信息
- 新增完整对话消息 / 事件 / 状态变更持久化层
- 发布前二次确认
- 自动修复做真任务
- 失败态展示范围以 UI 图片为准
- 现有 `overview / tasks / releases / logs` tabs 按 UI 图取舍，图里没有就移除
- 先移动端
- 最终效果要和 UI 图一致，包含组件、切图、颜色、字体和整体视觉

补充建议：

- `projectId`、`displayName`、`publicHandle` 三层拆分是最稳的结构
- `projectId` 永不变，负责内部关联
- `displayName` 和 `publicHandle` 同步更新，负责 UI 和公开访问
- 旧 `publicHandle` 不应直接丢弃，应该进入 alias 表并永久保留重定向，避免历史链接立刻失效

## 1. 路由要不要真的改成多页面

### 选项

- A. 继续单页应用，只用抽屉和本地状态切换
- B. 增加真实路由：
  - `/shipnow`
  - `/shipnow/project/:projectName`
  - `/shipnow/preview/:projectName`

### 影响

- A 更快，改动小
- B 更符合设计包，也更利于刷新恢复、深链接和预览独立打开

### 需要你拍板的点

- 是否允许引入真实路由结构
- 如果允许，是否把 `/shipnow/project/:projectName` 作为默认工作台入口

## 2. 创建项目是否继续要求手填项目名

### 选项

- A. 保留 `name + title + prompt` 三项必填
- B. 只输入一句话需求，项目名自动生成，后续可编辑

### 影响

- A 保守，能最大程度复用现有逻辑
- B 更符合设计包的“对话式创建”，但要改创建流程和校验逻辑

### 需要你拍板的点

- 是否要把“项目名”从首屏必填项里拿掉
- 是否允许系统自动生成项目名

## 3. 首页模板 chips 的定位

### 选项

- A. 只是预填 prompt 的快捷入口
- B. 作为创建流程的明确第一步，点击后进入对应模板上下文

### 影响

- A 简单，适合快速实现
- B 更像完整产品心智，但会增加创建流状态管理

### 需要你拍板的点

- 模板只是辅助，还是必须作为正式入口

## 4. 右侧状态区要展示到什么粒度

### 选项

- A. 只展示状态、预览链接、线上链接、最近任务
- B. 额外展示发布记录、技术日志入口、项目设置
- C. 继续保留所有工程信息，但默认折叠

### 影响

- A 最清爽
- B 更贴近设计包
- C 最接近现有数据结构，但容易重新变成后台感

### 需要你拍板的点

- 工程信息要隐藏到什么程度

## 5. 是否要新增“消息 / 事件”持久化层

### 选项

- A. 暂不新增，只靠任务和发布记录渲染界面
- B. 新增消息或事件表，保存用户输入、ShipNow 回复、结果卡片

### 影响

- A 改动小，但对话感偏弱
- B 更符合设计包，也更利于回放和后续扩展

### 需要你拍板的点

- 是否接受新增一层持久化结构

## 6. 发布前确认要不要强制

### 选项

- A. 直接点发布就执行
- B. 先弹确认 sheet，再执行发布

### 影响

- A 简洁
- B 更符合设计包，也更安全

### 需要你拍板的点

- 是否要求发布前确认目标地址

## 7. 自动修复要不要先做成真任务

### 选项

- A. 先只做 UI 入口和提示，不新增任务类型
- B. 新增真正的自动修复任务或修复流程

### 影响

- A 适合分阶段落地
- B 功能完整，但实现复杂度更高

### 需要你拍板的点

- 自动修复是第一阶段必做，还是先留入口

## 8. 失败态的可见范围

### 选项

- A. 主界面只显示简短错误摘要，日志进高级区域
- B. 主界面显示摘要 + 下一步动作，日志默认可展开
- C. 主界面直接显示任务日志预览

### 影响

- A 最接近设计包的“收纳工程信息”
- B 平衡调试和用户理解
- C 最容易实现，但最像后台

### 需要你拍板的点

- 主界面日志可见到什么程度

## 9. 是否保留现有 overview / tasks / releases / logs tabs

### 选项

- A. 完全移除，改成抽屉和卡片
- B. 先保留在右侧高级区域，主界面不再显示

### 影响

- A 更符合设计包
- B 更稳，改动范围更小

### 需要你拍板的点

- 这一轮是否允许直接删掉 tabs 结构

## 10. Mobile-first 的落实优先级

### 选项

- A. 先桌面端重构，再补移动端
- B. 先移动端主工作流，再扩展桌面端

### 影响

- A 更容易在现有代码上推进
- B 更符合设计包的产品方向

### 需要你拍板的点

- 这一轮要不要以移动端体验为第一优先级
